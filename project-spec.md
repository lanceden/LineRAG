# 璿恩智慧客服系統部署規劃案

## 一、專案背景

針對未來將導入之 AI 智能客服系統，服務對象涵蓋多個 B 端商業用戶與 C 端使用者，需具備穩定的地端推理能力與可擴展性，以支援 LINE 訊息串接、官網自訂對話框、RAG 檢索、對話記錄管理等模組。

---

### 📌 特色

* 模型與 RAG 可完全私有部署，資料不出外部。
* 預留多卡插槽，可日後升級至 2x5090、或部署獨立 embedding node。
* 成本控制，無需長期 API Token 支出。

---

### 2. 雲端主機（租用）

| 項目     | 規格建議                         | 說明                             |
| -------- | -------------------------------- | -------------------------------- |
| GPU      | A100 / H100（依照廠商方案）      | 通常計費以秒為單位，需精準控流量 |
| 雲平台   | AWS / GCP / RunPod / Lambda Labs | 可搭配容器化推理環境部署模型     |
| 計費模式 | 時數 / Token / 容量流量 計費     | 價格彈性但成本累積速度快         |
| 架構彈性 | 高，適合多地佈署                 | 可做負載均衡與容錯備援           |

#### 📌 雲端主機特色

* 快速佈署，無需維護硬體。
* 可配合 autoscaling 並行服務多客戶。
* 適合 PoC 與短期爆量測試階段使用。

## 三、成本初估（每月）

| 類型 | 項目               | 成本估算                                          |
| ---- | ------------------ | ------------------------------------------------- |
| 地端 | 一次性設備採購     | 約 NT\$ 350,000 \~ 400,000（單卡5090版本）        |
| 地端 | 月耗電 / 維護      | 約 NT\$ 3,000 \~ 5,000                            |
| 雲端 | GPU 推理費用       | 依 Token 或時數，平均 NT\$ 15,000 \~ 60,000+ / 月 |
| 雲端 | 儲存 / API Gateway | 依廠商約 NT\$ 2,000 \~ 10,000 / 月                |

## 四、雲端與地端部署選擇比較

### ✅ 選擇雲端部署的情境

* 需要快速上線驗證功能（如 PoC 或展示階段）
* 適合需求變動大、使用量不穩定的應用情境
* 不具備維護硬體主機的人力與資源
* 有資料合規但無嚴格機敏資料限制者

### ✅ 選擇地端部署的情境

* 資料保密性與控管需求高（如醫療、金融、內部對話）
* 希望避免長期 token 成本與流量費用
* 有穩定需求量且可預期擴充規模
* 已具備維運能力，或願意投入建置與 DevOps 專業資源

### 🧾 總結比較

| 項目     | 雲端主機         | 地端主機           |
| -------- | ---------------- | ------------------ |
| 建置速度 | 快速上線         | 前期需準備         |
| 前期成本 | 幾乎為零         | 較高（一次性支出） |
| 每月成本 | 難預測、可能爆量 | 穩定可控           |
| 資料掌控 | 外部平台         | 完全內部控管       |
| 擴充性   | 彈性佳           | 須預留規劃         |
| 維運需求 | 少               | 需 DevOps 支援     |

---

## 五、建議部署策略（混合）

1. 地端主機作為主推理與檢索中心，資料留存本地。
2. 雲端僅作為備援 / 高峰調度。
3. 前期先以單主機部署 + 多租戶架構驗證。
4. 擴充時導入小型 Worker Node 或第二主機，支援多租戶分流。

---

## 六、後續擴充與維運重點

* 若採 Ollama，僅支援單卡部署，需手動指定 CUDA\_VISIBLE\_DEVICES 切換 GPU，無法自動平衡推理工作負載
* 改用 vLLM 可支援單機雙卡或多機多卡部署，具備 OpenAI API 相容性與高併發能力，適合正式對外商用場景
* vLLM 啟動方式如下（建議在 Conda 虛擬環境中安裝）：

```bash
conda create -n vllm-env python=3.10 -y
conda activate vllm-env
pip install vllm
python -m vllm.entrypoints.openai.api_server \
  --model TheBloke/Qwen2-7B-Chat-AWQ \
  --tensor-parallel-size 2
```

* 搭配 FastAPI 可直接串接既有 `/ask` 與 `/webhook` 路由，將原本 Ollama 呼叫方式改為 `openai.ChatCompletion.create(...)`
* vLLM 支援 kv-cache、batching 與 OpenAI API 格式，適合 LINE Bot、RAG 問答、多租戶客服擴展應用
* 建議後續將 `StreamingResponse` 也改為支援 vLLM 的 stream 格式（`stream=True`），提升即時互動體驗

## 七、負載與使用者併發初估

以單張 RTX 5090 為例，搭配 Qwen2-7B（INT4 推理模式）：

| 項目               | 預估數值     | 說明                                    |
| ------------------ | ------------ | --------------------------------------- |
| 單輪推理延遲       | 約 1\~1.5 秒 | 單輪回答 150\~300 tokens                |
| 單卡同時處理對話   | 約 20\~30 人 | 每人每 5\~10 秒一輪互動，具快取優化情境 |
| 最大併發數（極限） | 約 40\~50 人 | 模型效能瓶頸，僅適合短輪快速問答        |
| 穩定建議負載       | 20 人以下    | 維持回應品質與資源餘裕                  |

> 📌 若需同時服務多個 B 端或 50+ C 端會員互動，建議擴充第二張 GPU 或採主從分流結構。

---

## 八、總結

地端主機雖有前期投入成本，但長期可控、可擴充、資料安全性高；雲端部署則具備彈性與便利性，適合作為高峰備援或企業級需求導入階段使用。建議採混合式策略，依照預算與使用量循序擴展。
