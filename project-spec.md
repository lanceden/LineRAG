# 璿恩智慧客服系統部署規劃案

## 一、專案背景

針對企業導入 AI 智能客服系統需求，專注於單租戶深度優化架構，提供穩定的地端推理能力與資料隱私保護，支援 LINE 訊息串接、官網自訂對話框、RAG 檢索、對話記錄管理等核心功能。本系統採用單機優化設計，確保每個客戶擁有獨立且高效能的AI客服環境。

---

* 成本控制，無需長期 API Token 支出。

### 2. 雲端主機（租用）

| 項目     | 規格建議                         | 說明                             |
| -------- | -------------------------------- | -------------------------------- |
| GPU      | A100 / H100（依照廠商方案）      | 通常計費以秒為單位，需精準控流量 |
| 雲平台   | AWS / GCP / RunPod / Lambda Labs | 可搭配容器化推理環境部署模型     |
| 計費模式 | 時數 / Token / 容量流量 計費     | 價格彈性但成本累積速度快         |
| 架構彈性 | 高，適合多地佈署                 | 可做負載均衡與容錯備援           |

#### 📌 雲端主機特色

* 快速佈署，無需維護硬體。
* 可配合 autoscaling 並行服務多客戶。
* 適合 PoC 與短期測試階段使用。

## 三、技術架構決策考量

### ✅ 地端部署技術優勢

* **資料隱私保護**：完全本地化處理，符合金融、醫療等高隱私要求
* **效能可控**：專用硬體資源，回應時間穩定可預測
* **成本透明**：無使用量計費，長期運營成本固定
* **技術自主**：完整技術掌控，可依需求客製化調整

### ⚠️ 地端部署技術要求

* **硬體投資**：需要專業 GPU 硬體和散熱系統
* **維運能力**：需要 DevOps 和系統管理專業人員
* **擴容規劃**：需要預先規劃硬體擴充方案
* **備援機制**：需要建立適當的備份和災難恢復機制

## 七、🔄 模型切換策略（開發 vs 上線）

為避免開發階段使用小模型、上線後切換大型模型導致效能瓶頸或架構崩潰，建議採用「模型可插拔」設計：

開發階段：使用 Qwen2.5-VL-3B-Instruct-AWQ 或 MiniCPM-V 進行流程模擬與介面開發。

上線階段：切換至 Qwen2.5-VL-7B/32B-Instruct（AWQ 量化），只需調整模型路徑與推理引擎參數。

架構抽象化：推理層與 API 層分離，前端不依賴模型細節，可快速切換模型版本。

效能預估：根據 RTX 5090 的併發能力，Qwen2.5-VL-7B-AWQ 可支援 20–30 人穩定使用，32B 則建議升級雙卡或雲端部署。

🖼️ vLLM 多模態支援說明
vLLM 推理引擎目前已支援多模態模型（如 Qwen2.5-VL、Phi-3.5-Vision），可處理圖像輸入與文字問答：

圖像輸入格式：支援 multi_modal_data={"image": PIL.Image}，可處理單張或多張圖片。

Prompt 處理：自動解析 <image> token，搭配 BaseMultiModalProcessor 對應圖像特徵。

推理引擎整合：vLLM 可與 FastAPI 結合，支援 async API 與 streaming 回應，適合高併發場景。

部署建議：使用 INT4 量化模型（AWQ）搭配 --gpu-memory-utilization 與 --max-num-seqs 調整併發能力。

📌 若使用 LM Studio 或 Ollama，需確認是否支援多模態 prompt；vLLM 則建議搭配 Hugging Face Transformers 模型與 PIL 圖像處理。

## 九、部署與維運指南

### ✅ 推薦部署步驟

1. **硬體準備**：按照建議規格配置主機和GPU
2. **環境設定**：安裝必要的系統套件和依賴項目
3. **模型部署**：配置 vLLM 和向量資料庫
4. **服務啟動**：運行 FastAPI 後端和 Next.js 前端
5. **測試驗證**：進行完整功能測試和效能評估

### ✅ 維運重點注意事項

* **定期備份**：資料庫和向量檔案定期備份
* **模型更新**：根據業務需求更新AI模型
* **效能監控**：持續監控系統資源使用情況
* **日誌管理**：保存系統運行和對話日誌
* **安全更新**：定期更新系統套件和安全補丁
